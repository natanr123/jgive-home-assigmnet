# i18n Design — Rails YAML as Single Source of Truth, Exported to JSON for React

## 1. TL;DR

- **`i18n-js` v4 gem** (`fnando/i18n-js`) is the single bridge: all UI strings live in `config/locales/{he,en}.yml` under a **`frontend:`** namespace; `config/i18n.yml` exports *only* that namespace to `app/javascript/locales/{locale}.json` via a `patterns:` glob. YAML is canonical, JSON is a generated-but-committed artifact.
- **Build-time static `import`, not runtime `fetch`** — esbuild's native JSON loader inlines the catalog into the ESM bundle (propshaft-hashed, zero extra round-trip, no flash). Per-locale lazy-load via `--splitting` is deferred until a second locale actually ships.
- **`i18n-js` v4 npm runtime** (`new I18n()` + `.store()` + `.t()`), wrapped in a **module singleton** `app/javascript/lib/i18n.ts` — *not* a React Provider. The singleton works inside React Router loaders/actions (which run outside the component tree) and in components alike.
- **Locale is set exactly once on boot** in `application.tsx`, read from the server-rendered `<html lang>` attribute (set by ERB from `I18n.locale`), before `createRoot`. The same value drives `dir` and parametrizes `format.ts`. No flash, one source.
- **YAML stays the source of truth by construction**: the exported JSON is **committed**, so a CI `i18n export` + `git diff --exit-code` actually catches stale artifacts; a scoped `rake i18n:verify` enforces he/en `frontend` key parity. Because the JSON is committed, dev needs no auto-export hook — refresh with `npm run i18n:export` after editing a YAML; prod re-exports during asset precompile.
- **Take-home scope**: app stays Hebrew-only and RTL; `en.yml` is seeded as a *proof of the seam* (fallback + key parity), not wired to a locale switcher. DB content is untranslated. Pluralization is used for the one genuine plural (`months`); everything else is a flat lookup. Total review surface: ~6 new/changed files + 14 mechanical call-site edits.

## 2. Source of truth & the gem

**Gem** (`Gemfile`):
```ruby
gem "i18n-js", "~> 4.2"
```
v4 is config-file driven (`config/i18n.yml`) and ships an `i18n` CLI. This is the critical version split: v3 used `I18n.config.export` and a mutable `I18n.translations` object; v4 uses `config/i18n.yml` + the `i18n` binstub on the Ruby side and `new I18n()` + `.store()` on the JS side. We target v4 end-to-end. The exact v4 CLI surface — `init`, `export`, `version`, `plugins`, `lint:translations`, `lint:scripts` — matters below: note in particular there is **no** `i18n check` and **no** `i18n watch` subcommand (both are easy to assume from v3-era memory but do not exist in v4).

**Rails locale config** (`config/application.rb`, inside the `Application` class):
```ruby
config.i18n.default_locale  = :he
config.i18n.available_locales = [:he, :en]
config.i18n.fallbacks = [:en]  # fall back to :en so English-only framework
                               # messages (ActiveRecord errors, etc.) still
                               # resolve when the locale is :he
```
A subtlety caught by the test suite (as-built): `config.i18n.fallbacks = true` falls back to the *default* locale (`:he`), which leaves `:he` with no fallback — so ActiveRecord's English-only validation messages ("can't be blank") stop resolving once `:he` is the default, and the GraphQL mutation specs that assert those messages break. `fallbacks = [:en]` gives every locale `:en` as a last resort (`:he → :en`), which is the conventional direction for framework strings. (This is the *opposite* direction from the React/`i18n-js` runtime, where `defaultLocale = "he"` so a frontend miss falls back `en → he` — different layer, different concern; our `frontend` catalog is complete in both locales so it rarely fires either way.)

**`config/i18n.yml`** (scopes the export — this is the line that keeps server-only strings off the client). The filter key is **`patterns:`** (a list of globs with `*` wildcards and `!`-prefixed exclusions), *not* an `only:` key:
```yaml
translations:
  - file: "app/javascript/locales/:locale.json"
    patterns:
      - "*.frontend.*"   # ONLY the frontend namespace ships to the browser
```
Three things to get right, all verifiable by running `bundle exec i18n export` once and reading the output:
1. **The per-file placeholder is `:locale`, not `%{locale}`.** `%{locale}` is the *v3* syntax; in v4 it is a literal and would write a single file named `%{locale}.json`. `:locale` expands to one file per locale (`he.json`, `en.json`); `:digest` (MD5) is also available. *(This is the one bug that surfaced only at runtime — the draft inherited v3 muscle-memory; running the export caught it.)*
2. **Patterns match the full dotted path *including* the locale segment** (`he.frontend.donate`), which is why the leading `*.` is required — a bare `"frontend.*"` would match nothing because every real key starts with the locale. (The README's own canonical example is the exclusion form `"!*.activerecord.*"`, same shape.)
3. The intent: `activerecord.errors.*`, mailer copy, Sidekiq/Devise strings, etc. never reach the bundle. Anything React must see is deliberately placed under `frontend:`. The equivalent exclusion form (`"*"` then `"!*.activerecord.*"`, …) is the alternative if a future surface needs almost-everything-minus-server; the allowlist `"*.frontend.*"` is the tighter, take-home-appropriate choice. *(Verified as-built: exported `he.json`/`en.json` contain only the `frontend` subtree.)*

**`config/locales/he.yml`** — mirrors today's `he.ts` nesting. Decision: **keep the camelCase keys verbatim** (`raisedSuffix`, `tabs.recentDonations`, `pendingBadge`). YAML does not require snake_case; preserving the existing keys turns 14 call-sites into a pure `he.X` → `t("X")` substitution with zero key-rename churn and zero risk of a typo'd rename. (A snake_case "to match Rails convention" variant was considered and rejected: the convention buys nothing for a frontend-only namespace and multiplies the diff. Defensible either way; minimal-diff wins for a take-home.)

```yaml
he:
  frontend:
    raisedSuffix: "גויסו"
    goal: "יעד"
    donorsCount: "מספר תורמים"
    donate: "לתרומה"
    bit: "bit"
    bitDisabled: "לא פעיל בדמו"
    copyLink: "העתקת קישור"
    linkCopied: "הקישור הועתק"
    taxDeductible: "תרומה מוכרת לזיכוי מס:"
    tabs:
      about: "על הפרויקט"
      recentDonations: "תרומות אחרונות"
      ambassadors: "לוח שגרירים"
      groups: "קבוצות"
      organization: "על העמותה"
      updates: "עדכונים"
    comingSoon: "בקרוב"
    # ... all remaining strings, 1:1 with he.ts (the full ~90-key set in app/javascript/locales/he.ts) ...
    recurringLabel: "הוראת קבע"
    months:                       # the ONE real plural — see §5
      one: "חודש"
      other: "חודשים"
    anonymous: "תורם/ת אנונימי/ת"
    thankYouTitle: "תודה רבה על תרומתך! 🧡"
```

**`config/locales/en.yml`** — replaces the Rails stub `hello: "Hello world"`; provides full key parity so `rake i18n:verify` passes and the seam is proven:
```yaml
en:
  frontend:
    raisedSuffix: "raised"
    goal: "Goal"
    donate: "Donate"
    tabs:
      about: "About"
      recentDonations: "Recent donations"
    months:
      one: "month"
      other: "months"
    # ... full parity with he ...
```

**Export command** (binstub generated by `bundle exec i18n init`, then run on demand):
```bash
bundle exec i18n export   # writes app/javascript/locales/{he,en}.json
```

**`.gitignore` — the exported JSON is *committed*, not ignored.** A tempting analogy says to gitignore it like the esbuild output ("it's generated, so don't track it"). That analogy is false: `/app/assets/builds/*` (ignored) is never used as a freshness oracle, whereas the whole point of the JSON gate below is `git diff`, and **`git diff` only inspects tracked files** — ignoring the JSON makes the gate a permanent no-op (vacuously green). So we add **no** ignore entry for `locales/*.json`; the catalog is reviewable in PRs and the diff actually polices staleness. (The esbuild output stays ignored as before; only the i18n JSON changes policy.)

## 3. Getting JSON into React

**Build-time import — recommended; runtime fetch — rejected.** The bundle is ESM emitted to `app/assets/builds` and served propshaft-hashed. A static `import he from "../locales/he.json"` lets esbuild inline the catalog: no extra HTTP request, no loading state, no flash-of-untranslated-content, and the catalog is cache-busted with the bundle. A runtime `fetch("/assets/he.json")` would add a round-trip on first paint and force every consumer to handle "not loaded yet" — strictly worse for a single-locale app whose whole catalog is ~3 KB.

**Runtime: `i18n-js` v4 npm package — recommended over a hand-rolled `t()`.** A custom-reducer `t()` (`key.split('.').reduce(...)`) is tempting at ~6 lines, but it does not handle interpolation or the `months.one/other` plural. `i18n-js` is ~4 KB gzipped, gives `%{count}` interpolation, a pluralizer, and fallbacks for free, and is the matched JS half of the gem (no API to invent or defend). Pick the gem's own runtime.

`package.json`:
```jsonc
"dependencies": {
  "i18n-js": "^4.5.0",
  // ...existing (react, react-dom, react-router, @rails/activestorage)
}
```
(`@types/i18n-js` is **not** needed — the v4 npm package ships its own types via a `typings` field. Verified by inspecting the published tarball; do not add the v3-era `@types/i18n-js`, it would conflict.)

**`tsconfig.json`** — the repo's current config has `esModuleInterop: true` but **not** `resolveJsonModule`, so the `import he from "../locales/he.json"` will fail typecheck until we add it:
```jsonc
"compilerOptions": {
  // existing: target es2022, module esnext, moduleResolution bundler, strict, esModuleInterop, ...
  "resolveJsonModule": true
}
```
Note also the current `"types": ["react", "react-dom"]` line restricts ambient types; it does **not** affect the `i18n-js` package types (those resolve through the import, not `@types`), so no change is needed there. This is a real edit to a real file — confirmed `tsconfig.json` exists and lacks `resolveJsonModule` today.

**TypeScript key-safety — honestly an open trade-off, not a solved one.** `i18n.t()` is stringly-typed, so `t("tabs.abuot")` (typo) compiles and returns a missing-translation string at runtime; `rake i18n:verify` checks *cross-locale parity*, **not** that a call-site key exists, so nothing in CI catches the typo. This is a genuine regression from today's `he.tabs.about` object access (compile-checked via `as const`). Two honest options, and we should pick in review rather than pretend it's decided:
- **(a) Restore safety with a small generator.** A ~15-line script derives a `TranslationKey` union from `he.json` into a `// @generated keys.d.ts`, and we type the wrapper `t(key: TranslationKey, opts?): string`. Real autocomplete/typo-safety back; cost is one generated file to maintain and regenerate alongside the JSON.
- **(b) Accept the loss.** Type the key as `string`, lean on a visible `[missing "…"]` render (see §5) and `rake i18n:verify` for parity, and state plainly in review: "we gave up compile-time key safety; a typo'd key renders a missing-translation marker, which is visible but not gated."

This doc does **not** ship the generator as a fait accompli; (b) is the default for take-home scope, (a) is the one-file upgrade if the reviewer wants the `as const` guarantee back.

**Per-locale lazy-load.** Deferred. The esbuild command can add `--splitting` (output is already `--format=esm`, the prerequisite) and the singleton would `await import('./en.json')` on switch. Not built now because there is no locale switcher and the catalog is tiny; documented as the exact one-line build change for when a second locale goes live.

## 4. Build & dev integration (the heart of "best practice")

The invariant: **JSON is never edited by hand and never goes stale.** Because the JSON is now committed (§2), staleness is enforced primarily at *merge* time, with a best-effort dev-time regeneration so the working tree rarely lags.

**Production export is a Rake hook, decoupled from esbuild.** Running `bundle exec i18n export` boots the Rails app to read `I18n.backend`. Wiring that into a `prebuild` npm hook means every `npm run build` re-boots Rails — and during `assets:precompile → javascript:build → npm run build`, that's a **nested Rails boot inside the asset-precompile Rake process** (slow, and a double-load hazard in some deploy images). So for prod we hook the Rake graph directly:
```ruby
# lib/tasks/i18n.rake
namespace :i18n do
  task :export do
    sh "bundle exec i18n export"
  end
end
Rake::Task["assets:precompile"].enhance(["i18n:export"])
```
`i18n export` runs **once**, in the Rake process that's already booted Rails, before assets compile. Production deploy gets fresh JSON without a nested boot.

**Dev: a manual `i18n:export` script — *no* `prebuild` hook (revised as-built).** The draft proposed an npm `prebuild` hook so `npm run build` would auto-export. In practice that hook is harmful: jsbundling-rails' `javascript:build` runs `npm run build` *during* `assets:precompile`, so `prebuild` would fire a **second, nested Rails boot inside the precompile** (on top of the Rake hook below) — exactly the double-load the prod section warns about. So the shipped `package.json` keeps only the manual script:
```jsonc
"scripts": {
  "i18n:export": "bundle exec i18n export",
  "build": "esbuild app/javascript/application.tsx --bundle --sourcemap --format=esm --outdir=app/assets/builds --public-path=/assets",
  "typecheck": "tsc --noEmit",
  "e2e": "playwright test"
}
```
This keeps `npm run build` pure esbuild (no Rails boot) — confirmed it builds in ~56ms. Dev doesn't *need* an auto-export hook because **the JSON is committed**: a fresh clone already has it, and esbuild imports the tracked file. The known gap: after editing a locale YAML you must run `npm run i18n:export` (or `bundle exec rake i18n:export`) to refresh the JSON — a `.yml` edit mid-`--watch` does not auto-regenerate it. We do not paper over this with a fake `i18n watch` process (no such v4 subcommand). If live-reload-on-YAML is ever wanted, adopt the gem's *actual* watch story — the `listen` gem in `config/initializers/i18n.rb`, `guard-i18n-js`, or the watchman `bin/i18n-watch` script — owning that dependency explicitly.

`Procfile.dev` therefore stays as-is (no invented fourth process):
```
web: env RUBY_DEBUG_OPEN=true bin/rails server
js: npm run build -- --watch
worker: bundle exec sidekiq
```

**`bin/setup`** — no change required (the committed JSON is already present; `npm run build` is pure esbuild). Keep it minimal.

**CI freshness gate** (the merge-time guard — now actually functional because JSON is committed):
```yaml
- run: bundle exec i18n export
- run: git diff --exit-code app/javascript/locales/   # fails if committed JSON differs from a fresh export
- run: bundle exec rake i18n:verify                   # he/en `frontend` key parity (scoped, noise-free)
```
Because the JSON is **tracked**, `git diff --exit-code` genuinely detects "a dev changed YAML but forgot to commit the regenerated JSON." For parity we use a **scoped `rake i18n:verify`** rather than `i18n lint:translations` — and this is an as-built correction worth calling out: `i18n lint:translations` lints the *entire* I18n backend, so Rails' English framework defaults (`en.number.*`, `en.time.*`, `en.support.*`) all show as "extraneous" against Hebrew (the default locale, which ships no framework translations) — dozens of false failures, and its `ignore:` option is exact-match only, so suppressing them is impractical. `rake i18n:verify` (in `lib/tasks/i18n.rake`) instead diffs the `frontend` key sets of the two *exported* JSON files — exactly what ships to the browser. Together: the diff proves the committed artifact is reproducible from YAML; the verify proves `he`/`en` are in sync (it reports `85 frontend keys present in both`).

## 5. The React migration

**Singleton runtime** — `app/javascript/lib/i18n.ts` (new):
```typescript
import { I18n } from "i18n-js";
import he from "../locales/he.json";
import en from "../locales/en.json";

export const i18n = new I18n({ he, en });
i18n.defaultLocale = "he";
i18n.enableFallback = true;          // en -> he where a key is missing (default is false; we opt in)

// All app keys live under "frontend.", so default the scope once here.
export function t(key: string, opts?: Record<string, unknown>): string {
  return i18n.t(`frontend.${key}`, opts);
}
```
Defaulting the `frontend.` prefix inside `t()` keeps every call-site reading `t("tabs.about")` — identical shape to today's `he.tabs.about` — while the namespace separation lives entirely in YAML/config. The singleton is importable from loaders/actions, so `campaignLoader` can `i18n.t("frontend.notFound")` with no Provider in scope.

**Missing-key behavior is visible, not silent.** The v4 default `missingBehavior` is `"message"`, so an unresolved key renders `[missing "he.frontend.x" translation]` (confirmed in the package source). That is *ugly but loud* — acceptable for a seam where a missing key is a bug we want to see, not hide. With `enableFallback = true` an `en` miss falls back to `he` first; only a key missing in *both* locales shows the marker. We accept this rendering; if a softer empty-string were ever wanted, `missingBehavior` is configurable, but loud-and-visible is the right default for catching drift.

**Boot — `application.tsx`** (locale set once, before mount, no flash):
```typescript
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import { RouterProvider } from "react-router/dom";
import { i18n } from "./lib/i18n";
import { setLocale } from "./lib/format";
import { router } from "./router";
import "./styles/base.css";

// Validate, don't cast: the raw attribute could be "", "he-IL", etc.
const el = document.getElementById("root");
const locale = el === null ? "he" : (document.documentElement.lang === "en" ? "en" : "he");
i18n.locale = locale;            // set ONCE, at module eval, before any component renders
setLocale(locale);               // thread the same value into Intl formatters
// dir already set server-side (see ERB below); no JS flip, no glitch.

if (el) {
  createRoot(el).render(
    <StrictMode>
      <RouterProvider router={router} />
    </StrictMode>
  );
}
```
Two deliberate points: (1) These boot side-effects are **top-level module statements**, run once at module evaluation — *not* in a component effect — so `StrictMode`'s double-render does not double-apply them. Do not "fix" this into a `useEffect`. (2) The locale is **validated, not cast**: a naive `document.documentElement.lang as "he" | "en"` cast lies if ERB ever emits `he-IL` or empty, and would make `format.ts`'s `Record<Loc, …>` lookups return `undefined` → crash. The `=== "en" ? "en" : "he"` guard removes that sharp edge for one extra clause.

**Server sets `dir`/`lang` from one source** — `app/views/layouts/application.html.erb`:
```erb
<html dir="<%= I18n.locale == :he ? 'rtl' : 'ltr' %>" lang="<%= I18n.locale %>">
```
The shell view (`app/views/shell/show.html.erb`) is just `<div id="root"></div>` and needs no change — it renders inside this layout, so `<html lang>` is authoritative and JS reads it. Because `I18n.locale` is `:he` by default and there is no locale-routing yet, this renders `dir="rtl" lang="he"` exactly as today, but now from the single Rails source instead of a hardcoded literal.

**`format.ts` parametrized from the same boot value** (no prop drilling, formatters cached per-locale). Today the file hardcodes `he-IL`/`ILS` and a single `RTF`; the parametrized form:
```typescript
type Loc = "he" | "en";
let active: Loc = "he";
export function setLocale(loc: Loc) { active = loc; }

const ils: Record<Loc, Intl.NumberFormat> = {
  he: new Intl.NumberFormat("he-IL", { style: "currency", currency: "ILS", maximumFractionDigits: 0 }),
  en: new Intl.NumberFormat("en-US", { style: "currency", currency: "USD", maximumFractionDigits: 0 }),
};
export function formatILS(cents: number): string { return ils[active].format(cents / 100); }

const rtf: Record<Loc, Intl.RelativeTimeFormat> = {
  he: new Intl.RelativeTimeFormat("he", { numeric: "auto" }),
  en: new Intl.RelativeTimeFormat("en", { numeric: "auto" }),
};
// relativeTime() body unchanged except RTF -> rtf[active]; UNITS table unchanged.
```
Currency-by-locale is wired but inert while Hebrew-only — note the live URL carries `/he/ils/`, so currency is genuinely a separate axis from locale; this leaves the seam visible without claiming to implement currency switching.

**Before/after — `DonationCard.tsx`** (the real interpolation/plural case):

*Before* (string-concat plural that is wrong for `recurringMonths === 1`):
```typescript
import { he } from "../locales/he";
// ...
{he.recurringLabel}
{donation.recurringMonths ? ` · ${donation.recurringMonths} ${he.monthsUnit}` : ""}
```
*After* (the `months.one`/`months.other` plural picks חודש vs חודשים):
```typescript
import { t } from "../lib/i18n";
// ...
{donation.pending && <span className={styles.pending}>{t("pendingBadge")}</span>}
{donation.recurring && (
  <span className={styles.recurring}>
    {t("recurringLabel")}
    {donation.recurringMonths
      ? ` · ${donation.recurringMonths} ${t("months", { count: donation.recurringMonths })}`
      : ""}
  </span>
)}
// ...
<div className={styles.name}>{donation.displayName ?? t("anonymous")}</div>
```
**Honest note on the pluralizer mechanism (it's easy to over-claim "CLDR" here).** `i18n-js` does **not** apply Hebrew CLDR here. Its default pluralizer is `make-plural`'s **English** rule (`one` for count===1, `other` otherwise), plus a `zero` branch when `count === 0`; only `ru`/`westSlavic` ship as extra registered locales, and **Hebrew is not registered** unless you call `i18n.pluralization.register("he", fn)`. For the month-count display the English rule's `one/other` split is exactly the distinction we need (1 → חודש, ≥2 → חודשים), so the **output is correct** — we just describe the mechanism truthfully as "i18n-js's default `one`/`other` pluralizer, correct for this month count," not as registered Hebrew CLDR (which is `one/two/many/other`). One caveat from the `zero` branch: `count === 0` would look up `months.zero` and, absent that key, render the `[missing …]` marker — but `recurringMonths` is only rendered when truthy (`? … : ""`), so count is always ≥1 and `zero` is never hit. (Defensibility: a single 1-vs-many split could even stay a flat `monthsUnit` with manual singular handling; we keep the plural because it's the *one* place the migration improves behavior — the old code always rendered חודשים even for a single month — and it costs one YAML key.)

Every other call-site is a mechanical `he.X` → `t("X")` swap. `donorsCount` and amounts use `toLocaleString`/`formatILS` and need **no** plural key.

(Phases 1–2 are pure additions; phase 3 is the only one that touches rendered output, isolating review risk.)

## 7. Trade-offs & deferred (take-home-honest)

- **JSON committed, not ignored.** Committing makes the catalog reviewable *and* makes the `git diff` freshness gate real; the cost is a generated file in PR diffs, which is acceptable and arguably useful. Ignoring it would have made the gate a no-op.
- **Typed keys are genuinely lost** with the stringly-typed `t()`, and `rake i18n:verify` does **not** catch call-site typos (only cross-locale parity). Either ship the ~15-line `keys.d.ts` generator to restore the `as const` guarantee, or accept the loss with a visible `[missing …]` render. Flagged as a real, undecided trade-off — not presented as solved.
- **Pluralizer is English-default `one`/`other`, not Hebrew CLDR.** Correct for the month count; described truthfully. Registering true Hebrew CLDR (`one/two/many/other`) is a `pluralization.register("he", …)` call deferred until a locale needs it.
- **Dev YAML-watch has a documented gap.** Mid-watch `.yml` edits need a manual `npm run i18n:export` (or adopt `listen`/`guard-i18n-js`/`bin/i18n-watch` as an explicit dependency). No fictional `i18n watch` process.
- **No locale switcher / no `/he/` `/en/` routing.** The seam is fully wired (catalogs, fallback, `dir` from `I18n.locale`, currency axis) but nothing flips the locale. Adding it later: a `scope "/:locale"` (or `before_action` setting `I18n.locale`) in routes, a locale segment in `router.tsx`, and `--splitting` + dynamic `import()` in the build.
- **DB content untranslated** (decided): campaign name/story, charity about, donor names stay single Hebrew columns; documented future upgrade.
- **Prod export decoupled from esbuild.** `assets:precompile` is enhanced with a Rake `i18n:export` (one Rails boot in the already-booted Rake process), rather than nesting `bundle exec i18n export` inside `npm run build` during precompile.

## 8. Open questions for the interviewer

1. **Locale routing shape.** The live URL is `/he/ils/...` — when a switcher lands, is locale a URL path segment, a cookie/`Accept-Language`, or both? This decides whether `I18n.locale` is set by a routes `scope` vs a `before_action`, and whether React reads it from the URL or stays reading `<html lang>`.
2. **Currency vs locale coupling.** The URL treats `he` and `ils` as independent segments. Should currency be switchable independently of UI language (e.g. `/en/ils/`), or locked together? This affects whether `setLocale` should take a separate `currency` argument now.
3. **Typed keys: worth the generator?** Compile-time key safety (generated union, restoring the `as const` guarantee) or is a visible runtime `[missing …]` + `rake i18n:verify` parity sufficient for a project this size? (This is a real choice, not a formality — the parity check does not catch call-site typos.)
4. **Hebrew pluralization fidelity.** We use the default English `one`/`other` pluralizer (correct for the one month-count case). Do any future strings need true Hebrew CLDR categories, which would require `pluralization.register("he", …)`?
5. **Any server-rendered or emailed strings to translate?** Everything user-facing is React+GraphQL today, so the `frontend:` namespace is the whole client surface — confirm no mailer/server HTML needs i18n, otherwise those keys live *outside* `frontend:` (and the `"*.frontend.*"` pattern correctly keeps them off the browser bundle).
